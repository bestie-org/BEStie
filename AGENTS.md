## Project description

BEStie is a Bluetooth Low Energy (BLE) protocol translator. It acts as a GAP peripheral and GATT Client/Server.

On one side BEStie talks to Bosch Electric System (BES) eBike via Live Data Interface (LDI). It acts as GATT Client in this role. Protobuf definition for LDI data is stored in `proto/` along with specification .pdf. 

On the other side BEStie acts as a GATT Server for BLE Fitness Machine Service (FTMS) and connects to fitness tracking gear like bike computers or smart watches.

Most devices currently on the market don't understand LDI protocol. BEStie fills that gap by translating incoming LDI protobuf stream into FTMS power, speed and cadence notifications most fitness devices understand.

In case of both protocols BEStie is a GAP Peripheral and other devices are GAP Centrals. This is non standard in context of LDI but that's what Bosch's LDI spec dictates.

## Platform

Nordic nRF52832 and nRF52840, Cortex M4 with FPU and BLE radio.

This is deeply embedded, battery powered application with constrained resources. Running for months, optimally over a year on single battery charge is important.

nRF52832 has only 64kb of RAM total, after s132 softdevice takes its share that drops to about 40kb.
Keeping track of RAM usage is big part of code analysis you're expected to perform. Another big part is keeping track of worst case stack use.

### Event dispatch and scheduling

The SoftDevice is configured with NRF_SDH_DISPATCH_MODEL = 1 (APPSH) — BLE events are NOT processed inline in the SD ISR. Instead the SOC event NRF_EVT_RADIO_SESSION_IDLE triggers a scheduler event that polls BLE events and dispatches to observers. This poll runs INSIDE app_sched_execute().

App_timer is configured with APP_TIMER_CONFIG_USE_SCHEDULER = 1, so timer callbacks enter the same scheduler queue. It's also configured with APP_TIMER_V2 that controls which SDK implementation is used (`app_timer2.c`).

Consequence: both BLE observer chains and timer callbacks run in the same FIFO scheduler queue, at application priority (not interrupt context).

app_timer_start() and app_timer_stop() are safe to be called from interrupt context and have critical region (disable interrupts) guards for key operations. As an effect they are safe from concurrency standpoint. Proper atomic flags are used to keep track of timer states.

Similar pattern of using app_scheduler and timers should be reflected all over the codebase. All that interrupt handlers are meant to do are short running tasks that have to be executed with minimum latency. Everything else is pushed into main event loop via `app_sched_event_put()`.
